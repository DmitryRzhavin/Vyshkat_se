# ВышКат — интерактивный учёт парка

Консольное приложение на Python для учёта транспорта и вещей. Данные вводятся пользователем во время работы: в исходном коде нет заранее заданного демонстрационного парка. Приложение хранит данные в памяти до завершения процесса.

## Запуск на Ubuntu

Откройте каталог проекта в терминале VS Code, подключённом к виртуалке:

```bash
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m vyshkat.app
```

Если `venv` не установлен: `sudo apt update && sudo apt install python3-venv`.

В меню можно принять транспорт (успешный техосмотр или отказ по ответу пользователя), добавить шлем или зарядную станцию, посмотреть число единиц и расход энергии, список техники с простотой ≥ 6, полный инвентарный список, а также выйти.

Тесты и измерение покрытия:

```bash
pytest
pytest --cov=vyshkat --cov-report=term-missing
```

## Структура

- `domain.py`: модели транспорта/вещей, структурные интерфейсы `InventoryItem` и `EnergyConsumer`.
- `services.py`: `Fleet` хранит активы и считает отчёты; `FleetService` применяет сценарий приёмки; `ServiceCenter` задаёт контракт техосмотра.
- `container.py`: DI-контейнер связывает парк, прикладной сервис и реализацию техосмотра.
- `console.py`: интерактивный ввод/вывод, не содержит правила техосмотра или подсчёта отчётов.
- `app.py`: точка запуска.
- `tests/`: поведенческие тесты бизнес-логики и консольного интерфейса.

Суточное потребление суммируется по всем активам, реализующим `EnergyConsumer`, включая зарядную станцию. Велосипед можно ввести с нулевым расходом. Вещи не проходят техосмотр транспорта. Инвентарный номер уникален для всех типов активов.

## Архитектура и SOLID

- **SRP:** доменные модели находятся отдельно от учёта (`Fleet`), сценария приёмки (`FleetService`) и консольного взаимодействия (`ConsoleApp`).
- **OCP:** отчёты работают с `Transport`, а не с отдельными типами транспорта. Новый вид транспорта наследуется от `Transport`; чтобы пользователь мог выбрать его в консоли, тип регистрируется в таблицах `TRANSPORT_TYPES`/`TRANSPORT_LABELS` в `console.py`. Правила приёмки и отчёты при этом менять не надо.
- **LSP:** специализированные виды транспорта сохраняют контракт `Transport`: корректный инвентарный номер, простота 1–10, неотрицательный расход и совместимость с приёмкой и отчётами.
- **ISP:** отдельные протоколы `InventoryItem` и `EnergyConsumer` не заставляют шлем иметь расход энергии.
- **DIP:** `FleetService` зависит от протокола `ServiceCenter`, а конкретный `DefaultServiceCenter` создаётся в composition root (`container.py`).

Наиболее явно применён **DIP**: приёмка использует абстракцию `ServiceCenter`, а не конкретный класс проверки. Это позволяет тестировать сценарии с фейком.

Сознательно не создаётся отдельная сложная иерархия стратегий для каждого транспорта: пока у типов транспорта одинаковые правила приёмки и отчёта, достаточно общей модели. Новый тип требует небольшой регистрации в консольном меню, но не массовой правки бизнес-логики. Это избегает декоративных абстракций.

## DI и тестирование

DI-контейнер создаёт общий `Fleet`, `DefaultServiceCenter` и `FleetService`. В `tests/test_services.py::test_di_container_can_override_inspection_dependency` реальный провайдер техосмотра заменён фейком через `container.service_center.override(providers.Object(fake))`. Тест проверяет, что отказ фейка не добавляет транспорт. Также `test_failed_inspection_does_not_add_transport` фиксирует поведение отказа, а `test_beginner_threshold_is_inclusive_at_six` — границу правила для новичков. `tests/test_console.py` проверяет интерактивный ввод и понятный вывод.

## Обязательные вопросы

1. **Самый явный SOLID:** DIP в `FleetService` и `ServiceCenter`; связь конкретных объектов собрана в `container.py`.
2. **Ограниченный принцип:** OCP не полностью автоматизирует подключение нового транспорта к пользовательскому меню — нужно добавить его в таблицу типов интерфейса. При этом доменные отчёты и приёмка не меняются. Для небольшого консольного проекта отдельный плагинный механизм был бы избыточен.
3. **Расширение:** новый транспорт добавляется как подкласс `Transport` и регистрируется в меню; сотрудников нельзя добавить в текущий парк как транспорт, для них потребовались бы отдельные модель и сценарии. Склад запчастей можно представить отдельным типом `InventoryItem`; если он потребляет энергию — реализовать также `EnergyConsumer`.
4. **Тест и подмена:** тесты `test_di_container_can_override_inspection_dependency` и `test_failed_inspection_does_not_add_transport`; правило новичков фиксируется `test_beginner_threshold_is_inclusive_at_six`.
5. **Использование ИИ:** использовался как вспомогательный инструмент при разработке проекта: для обсуждения архитектуры, подготовки и улучшения отдельных частей реализации, а также покрытия реализации ДЗ тестами и тестовыми сценариями с поведением пользователя. Предложенные решения проверялись в контексте требований задания и запуском тестов
